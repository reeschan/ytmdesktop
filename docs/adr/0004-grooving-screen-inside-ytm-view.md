# Grooving の画面は YTM 画面の中に作り、LLM と API Key はメインプロセスに置く

Grooving の入口はサイドバーの「ライブラリ」の下に置き、Grooving の画面も YTM 画面の中央の領域を覆う形で YTM 画面の中に作る。一方で、LLM (Gemini / Claude / ChatGPT) の API Key を持って問い合わせるのはメインプロセスにする。YTM 画面がメインとやりとりするのは、利用者の操作の合図、候補の曲、YTM 画面への頼みごと (候補を集める・試聴する・キューを置き換える・保存する) とその結果、画面に出す状態だけで、API Key と LLM への問い合わせの中身は YTM 画面に渡さない。

ADR 0003 (曲の聞き取り) では、録音を YTM 画面の外に出した。あのとき外に出したのは、YTM 画面にマイクと画面の取り込みの権限を許したくなかったからである。Grooving が YTM 画面に求めるものは、ページの中の UI と、ログインしたまま YTM の内部 API を呼ぶことだけで、新しい権限は要らない。候補の曲の取得、試聴、キューの置き換え、プレイリストの保存は、どれも YTM 画面の中でしかできない。そのため、画面は YTM 画面の中に置いてよいと判断した。API Key は使った分だけ課金されるので、ADR 0003 と同じ理由でページの中に置かない。

## Considered Options

- **別のアプリ画面のウィンドウにする**: 既存の Vue の部品が使え、YTM の DOM の変化にも強い。しかし、入口がサイドバーに無いと開きにくい。また、候補集め・試聴・キューの操作はどれも YTM 画面に頼むことになるので、画面だけ外に出しても YTM 画面とのやりとりは減らない。利用者が「ライブラリの下」に置くことを選んだので採らなかった。
- **LLM も YTM 画面から呼ぶ**: やりとりは減るが、API Key を Google のページに渡すことになるので採らなかった。

## Consequences

- YTM がサイドバーや中央の領域の作りを変えると、入口と Grooving の画面が崩れうる。サイドバーを描き直されて入口が消えたら、足し直す作りにする。
- Grooving の進行の状態はメインが持ち、YTM 画面はメインから送られた状態のとおりに画面を出す (曲の聞き取りと同じ分け方)。
- 試聴とキューの置き換えは YTM のプレイヤーそのものを使うので、利用者が聴いていた曲とキューに触れる。試聴では元の曲と元の位置に必ず戻す。
- YTM のページのメインワールドのスクリプトは、Grooving の合図を偽造できる。同意がまだ無いとき (初回・設定で取り消した直後) に「履歴を送る」同意を保存させることもできる。既知の制約として受け入れる (2026-11-04、security-audit の指摘に対して利用者が決めた)。YTM 自身がもともと履歴を持っており、影響はキーの持ち主の LLM への送信に限られるため。API Key はメインから出ない。偽の合図で起こせる LLM の呼び出しと、プロンプトの大きさには、メインで上限を設ける (PBI-448)。
